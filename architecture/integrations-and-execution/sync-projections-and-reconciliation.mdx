---

Rule & Form automates the work that should happen after an inquiry, call, appointment, or completed job.

The automation system decides:

**What should happen? When should it happen? What would make it stop? Is it still safe and appropriate to do?**

External providers may execute messages, calls, calendar actions, or selected workflow steps.

They do not own the meaning of the automation.

 \<Callout icon="terminal" color="#8B5CF6"\> **For implementation** - Follow-Up & Automation owns Rule & Form automation semantics, eligibility, timing, cancellation, and progression. System Events and current Rule & Form domain state trigger decisions. Provider Commands execute required external actions. HighLevel workflows may implement selected provider-side execution, but their configuration is a representation of Rule & Form policy, not the canonical policy itself. \</Callout\>

```text
```

```text

        +
System Events

Lead created
Call missed
Message received
Appointment created
Appointment changed
Lead won
Lead lost
Job completed

        ↓

Follow-Up & Automation

policy
eligibility
timing

        ↓

durable follow-up state

        ↓

Provider Commands
and / or
managed provider workflow execution

        ↓

HighLevel / other providers

        ↓

        ↓

```

The automation system reacts to Rule & Form meaning.

It does not build product logic directly on raw provider payloads.

## The core principle

Automation is not a collection of disconnected provider workflows.

It is a Rule & Form policy applied to known business state.

```text
```

```text
NOT

HighLevel workflow 18
trigger 42
branch 7
wait step
SMS node
pipeline node


RULE & FORM

Missed Call Response
        ↓
eligible missed call
        ↓
send acknowledgment
        ↓
stop if customer responds
        ↓
surface resulting conversation
```

The provider implementation may change.

The product behavior should remain understandable.

**Automate the business rule, not the vendor screen.**

## What this system owns

Follow-Up & Automation owns:

- <br />automation policy identity<br />
- <br />trigger semantics<br />
- <br />eligibility<br />
- <br />timing<br />
- <br />action sequencing<br />
- <br />stop conditions<br />
- <br />expiration<br />
- <br />communication intent<br />
- <br />subject identity<br />
- <br />progression through an active follow-up<br />
- <br />customer and system cancellation<br />
- <br />provider execution intent<br />
- <br />automation history<br />
- <br />customer-visible activity where appropriate<br />

It does not own:

| Concern | Authority |
| :-- | :-- |
| Business facts | Business Record |
| Customer identity | Customer model |
| Lead state | Lead model |
| Job state | Job model |
| Conversation and Message identity | Operational domain |
| Appointment identity | Operational domain |
| Messaging capability readiness | Capability State |
| Provider credentials | Integration Connection |
| Provider object IDs | Provider Mapping |
| Retry execution | Command / workflow infrastructure |
| Provider delivery truth | Provider Event / reconciliation |

The automation system reads those authorities.

It does not duplicate them.

## Policies are explicit product logic

A follow-up behavior is represented as a named Rule & Form policy.

Examples include:

```text
```

```text
missed_call_response

new_lead_acknowledgment

unanswered_lead_follow_up

appointment_reminder

estimate_follow_up

past_customer_reactivation
```

V1 implements only the policies required by the first real customer loop.

The exact stable identifiers belong in [Naming, IDs & Conventions](/architecture/foundation/naming-ids-and-conventions).

### Policy is not visible copy

A policy identity may be:

```text
```

```text
missed_call_response
```

while customer-facing text says:

```text
```

```text
Sorry we missed your call. How can we help?
```

Changing the wording does not create a different automation policy.

Likewise, a provider workflow name is not policy identity.



V1 does not need a generic no-code automation language.

## Policies are versioned

Automation behavior changes over time.

For example:

```text
```

```text
missed_call_response v1

send after 60 seconds
```

may later become:

```text
```

```text
missed_call_response v2

send after 30 seconds
different approved wording
different suppression rule
```

That is a product change.

The version should be identifiable.

An active follow-up should not silently change meaning halfway through because someone edited a policy definition.

Conceptually:

```text
```

```text
Follow-Up Run

policy:
missed_call_response

policy_version:
2
```

The exact storage model may differ.

The invariant is reproducibility.



Prefer:

```text
```


```text
```


Provider events enter through their adapter and operational model first.

```text

System Event
```

## Current state still matters

An event explains what happened.

Current Rule & Form state determines whether the automation should still act.

Example:

```text
```

```text
LeadCreated
        ↓
follow-up scheduled
        ↓
customer calls business
        ↓
Lead becomes Active
        ↓
scheduled follow-up evaluates
current state
        ↓
skip unnecessary message
```

Do not assume that because an action was valid when scheduled, it remains valid hours later.

Every consequential step rechecks relevant current state before external execution.

**Scheduled intent is not permission to ignore what happened afterward.**

Conceptually:

```text
```

```text

stopped

expired

failed
```


```text

Provider Command
```

## Timing

Timing is part of the policy.

Examples:

```text
```

```text
immediately

after 1 minute

2 hours after inquiry

24 hours before appointment

3 days after estimate

6 months after completed Job
```

Timing should be durable.

Closing the browser does not cancel it.

Deploying new application code does not erase it.

### Due time is explicit

Conceptually:

```text
```

```text
next_action_at
2026-08-11T19:43:00Z
```

The workflow runner may be responsible for waking the work at that time.

The durable application state explains what should happen.

```text
```

```text
PostgreSQL
    owns follow-up state

Inngest / managed provider execution
    wakes and executes it
```

Do not make the workflow runner the only place where the existence of a scheduled follow-up can be discovered.

## Expiration

A delayed automation is not always still useful.

Example:

```text
```

```text
Missed call
7:42 PM

response intended:
7:43 PM

provider unavailable

retry finally possible:
next day 11:00 AM
```

Blindly sending the original "Sorry we missed your call" response sixteen hours later may be inappropriate, especially if the customer already reached the Business another way.

Policies therefore define meaningful expiration or freshness rules where needed.

```text
```

```text
action due
        ↓
provider unavailable
        ↓
retry window
        ↓
still timely?
    yes → continue
    no  → expire / skip
```

**Reliable automation does not mean executing stale intent forever.**

Automation is useful because it knows when to stop.

Common stop conditions may include:

```text
```

```text

customer called back

appointment booked

Lead won

Lead lost

Job created

customer opted out

contact method invalid

manual stop

required capability unavailable

automation expired
```

The exact conditions vary by policy.

### Stop conditions are checked before each step

Suppose a Lead follow-up is:

```text
```

```text
message now

message in 1 day

message in 3 days
```

If the Customer responds after the first message:

```text
```

```text
customer reply
        ↓
Conversation updated
        ↓
System Event
        ↓
Follow-Up Run stopped
        ↓
future scheduled messages suppressed
```

The system should not continue pestering someone who already responded.

## Manual activity can stop automation

A contractor may handle a Lead manually.

That activity should be able to suppress automation where the policy says it should.

Examples:

```text
```

```text
contractor sends manual reply

contractor marks Lead won

contractor marks Lead lost

contractor books appointment
```

Automation must not compete with the human operating the Business.

**Automation supports the response. It does not fight the response.**

## Missed-call response

Missed-call text-back is a core Rule & Form automation.

The semantic flow is:

```text
```

```text
incoming call
        ↓
call result normalized
        ↓
CallMissed
        ↓
policy eligibility
        ↓
required messaging capability usable?
        ↓
send acknowledgment intent
        ↓
Provider Command
        ↓
SMS transport
        ↓
Conversation / Message history
```

The automation does not begin merely because some provider emitted a call webhook.

Rule & Form first determines the normalized call outcome.

### Eligibility

A missed-call response may require:

```text
```

```text
call was genuinely unanswered

caller number available

number is eligible for messaging

Business messaging capability usable

policy enabled

no suppression condition

no equivalent response already sent
```

The exact call classification belongs to the communications integration.

This page owns the rule that automation operates on a normalized missed-call fact.

### Stable idempotency

One missed call must not generate several identical acknowledgments because:

```text
```

```text
provider redelivered event

workflow retried

worker crashed

webhook arrived twice
```

The automation uses stable identity tied to the underlying occurrence and policy.

```text
```

```text
CallMissed event
        +
missed_call_response policy
        ↓
one logical automation enrollment
```

Provider Commands then maintain their own idempotency guarantees.

## New Lead acknowledgment

Rule & Form may acknowledge a valid newly submitted Lead.

The required ordering is:

```text
```

```text
website submission
        ↓
Customer / Lead committed
        ↓
LeadCreated
        ↓
acknowledgment policy
        ↓
message intent
```

Never:

```text
```

```text
website submission
        ↓
send message
        ↓
hope Lead creation works afterward
```

The Lead remains durable even if messaging is unavailable.

### Acknowledgment is not successful follow-up

A message saying:

```text
```

```text
We received your request.
```

does not mean:

```text
```

```text
the contractor responded personally
```

The product should distinguish automated system activity from customer/operator activity where that distinction matters.

```text
        ↓

        ↓
wait
        ↓
still eligible?
        ↓
```

This policy should remain deliberately limited.

A Lead that becomes:

```text
```


## Appointment reminders

Appointment reminders operate on Rule & Form Appointment identity.

```text
```

```text
Appointment
        ↓
scheduled time
        ↓
reminder policy
        ↓
reminder action
```

If the appointment changes:

```text
```

```text

        ↓
rescheduled
        ↓
4:00 PM
```

the automation must not send reminders for stale appointment state.

Rescheduling should cancel or replace future reminder intent as required.

### Cancellation

If the Appointment is cancelled:

```text
```

```text

        ↓
stop
```

A reminder system that sends messages for cancelled appointments is not merely annoying.


```text

        ↓
follow-up policy
```


## Communication eligibility

Automation does not assume that because Rule & Form knows a phone number or email address it may use it for every purpose.

Before a communication action, Rule & Form evaluates the required channel and policy eligibility.

Conceptually:

```text
```

```text
Customer
        ↓
contact point
        +
communication evidence / status
        +
policy purpose
        +
Business capability
        ↓
eligible?
```

Where consent, opt-out, or other communication restrictions apply, those constraints are enforced centrally.

### Opt-out is authoritative

A valid opt-out or suppression state stops future communication covered by that restriction.

```text
```

```text
opt out
        ↓
record restriction
        ↓
stop eligible Follow-Up Runs
        ↓
prevent future prohibited actions
```

Do not rely solely on the provider to remember this state.

Provider enforcement may supplement Rule & Form's own communication eligibility.

## Locale


```text

```



```text

what next
```

## Managed provider workflows

Some automation may be efficiently executed through a provider-managed workflow.

2. <br />Provider configuration is inspectable and associated with the policy/version it represents.<br />

### Do not split one policy unknowably across systems

Avoid:

```text
```


```text
```

```text

provider implementation
current enrollment or status where observable
expected behavior
```

It should be:


```text

verifiable where possible
reconcilable where possible
```

A staff member manually creating a workflow during early provisioning is acceptable.

Leaving Rule & Form with no record of what was created is not.

**Manual setup is allowed. Invisible setup is not.**

## Capability dependencies

Automation cannot assume every channel is available.

Example:

```text
```

```text
missed_call_response
        ↓
requires

Business phone
        +
SMS
```

If SMS is:

```text
```

```text
In progress
```

the policy cannot truthfully behave as though the response was sent.

### Capability failure does not destroy the underlying event

```text
```

```text
CallMissed
        ↓
SMS unavailable
```

The missed call remains in Rule & Form history.

The automation may:

```text
```

```text
wait within policy window

use approved alternate channel

surface action internally

expire
```

according to policy.

It does not delete or rewrite the missed call.

### Automation capability state remains separate

Do not create a new customer-facing state system inside Follow-Up & Automation.

The existing Capability model answers whether SMS, booking, phone, and other capabilities can operate.

Automation consumes that result.

```text
```

```text

        ↓
request-service link or phone CTA
```

or:


```text

do not send
        ↓
surface internal/customer action
```

A fallback must be explicitly approved.

Do not improvise one at runtime because a provider failed.

If an SMS policy fails, do not automatically send email instead unless the policy explicitly permits that substitution and the destination is eligible.

```text
```

```text
SMS
        ≠
email
```

Communication channels have different expectations, availability, and eligibility.

## Idempotency

Automation protects against duplicate execution at several layers.

```text
```

```text
Provider Event deduplication
        ↓
System Event identity
        ↓
Follow-Up enrollment identity
        ↓
Follow-Up Step identity
        ↓
Provider Command idempotency
```

Each layer solves a different problem.

### One event should not create several runs

Conceptually:

```text
```

```text
LeadCreated:
event_123

policy:
new_lead_acknowledgment

        ↓

stable enrollment identity

        ↓

one Follow-Up Run
```

If the System Event is processed twice, Rule & Form recognizes the existing enrollment.

### One step should not create several commands

Likewise:

```text
```

```text
Follow-Up Run
step 1
send acknowledgment
```

should produce one logical Provider Command even if a worker retries.

## Concurrency

Multiple automations may potentially act on the same Lead or Customer.

That needs explicit policy.

Example:

```text
```

```text
new_lead_acknowledgment

and

unanswered_lead_follow_up
```

may intentionally coexist as stages of one customer journey.

But:

```text
```

```text
two separate unanswered-lead policies
```

should not unknowingly send competing messages.

V1 should use deliberate enrollment uniqueness and policy compatibility rather than attempting to build a generic automation-conflict solver.

### New events can supersede old intent

Example:

```text
```

```text
Lead new
        ↓
unanswered follow-up active

then

Lead won
        ↓
follow-up stopped
```

Current business state wins over stale future actions.

## Acceptance conditions

Follow-Up & Automation is working when:

- <br />A normalized Rule & Form System Event can trigger a named policy without exposing provider event vocabulary to the policy.<br />
- <br />Processing the same trigger more than once does not create duplicate Follow-Up Runs.<br />
- <br />A Follow-Up Run identifies the policy version and subject it is acting on.<br />
- <br />Scheduled actions survive the browser closing.<br />
- <br />Scheduled actions survive ordinary application deployments.<br />
- <br />A scheduled step reevaluates relevant current state before sending.<br />
- <br />A Customer reply can stop future unanswered-lead follow-up.<br />
- <br />A contractor reply can suppress automation where policy requires.<br />
- <br />Marking a Lead won stops incompatible sales follow-up.<br />
- <br />Marking a Lead lost stops incompatible sales follow-up.<br />
- <br />A cancelled Appointment cannot receive a reminder intended for the old active appointment.<br />
- <br />A rescheduled Appointment does not continue reminders for its stale time.<br />
- <br />One missed call cannot generate duplicate text-backs because a webhook was delivered twice.<br />
- <br />A Lead is persisted before its acknowledgment automation executes.<br />
- <br />Messaging provider failure cannot erase the Lead or missed call that caused the automation.<br />
- <br />A delayed action can expire instead of sending stale communication indefinitely.<br />
- <br />A provider outcome marked uncertain does not cause blind duplicate communication.<br />
- <br />An unavailable capability prevents the automation from pretending execution succeeded.<br />
- <br />A valid customer opt-out suppresses future communication covered by that restriction.<br />
- <br />Message variables resolve from Rule & Form concepts rather than provider custom-field names.<br />
- <br />Missing required variables follow an explicit fallback or prevent sending.<br />
- <br />Automated customer messages use controlled templates rather than unrestricted runtime generation.<br />
- <br />A HighLevel workflow may execute selected behavior without becoming the canonical automation policy.<br />
- <br />Rule & Form can identify which provider configuration represents a managed provider-side policy where applicable.<br />
- <br />Provider retries remain in the Provider Command layer rather than policy code.<br />
- <br />Business Hub can show useful automation activity without exposing workflow infrastructure.<br />
- <br />Workbench can explain why an automation started, acted, stopped, failed, or expired.<br />
- <br />Demo automation uses the same policy and execution path as production.<br />

## Foundation rules

1. **Rule & Form owns automation semantics.**<br />
2. **Providers may execute automation without owning its meaning.**<br />
3. **Automation triggers from normalized Rule & Form events and state, not raw provider vocabulary.**<br />
4. **Current state is rechecked before consequential scheduled actions.**<br />
5. **Automation policies have stable identity and version.**<br />
6. **Follow-Up Runs are durable Rule & Form state.**<br />
7. **One trigger and policy combination cannot create duplicate logical enrollments.**<br />
8. **Provider Command idempotency remains separate from automation enrollment idempotency.**<br />
9. **Automation steps express semantic intent rather than provider workflow nodes.**<br />
10. **Timing is durable and inspectable.**<br />
11. **Delayed actions may expire when their original intent is no longer timely.**<br />
12. **Stop conditions are first-class product logic.**<br />
13. **Customer engagement can stop automation.**<br />
14. **Contractor activity can stop automation where policy requires.**<br />
15. **Canonical Lead, Appointment, Job, Conversation, and Customer state outrank stale scheduled intent.**<br />
16. **A provider failure never erases the business event that triggered automation.**<br />
17. **A retrying Provider Command does not automatically mean the Follow-Up Run failed.**<br />
18. **An uncertain provider outcome is reconciled before a potentially duplicate action is attempted.**<br />
19. **Communication eligibility is checked for the specific destination and policy before execution.**<br />
20. **Opt-out and suppression state are enforced by Rule & Form, not delegated blindly to a provider.**<br />
21. **Channel substitution requires explicit policy.**<br />
22. **Automated operational messages use controlled, reviewable expression.**<br />
23. **Runtime AI does not receive unrestricted authority to invent and send customer communication.**<br />
24. **Managed provider workflows are implementation state, not canonical product logic.**<br />
25. **Manual early provider configuration is allowed. Untracked provider behavior is not.**<br />
26. **Capability State determines whether required communication infrastructure is usable.**<br />
27. **The automation layer owns sequence. The Provider Command layer owns external retry execution.**<br />
28. **Business Hub shows customer-relevant outcomes; Workbench exposes the machinery.**<br />
29. **V1 implements a few high-value policies deeply rather than building a general automation platform.**<br />
30. **New automation rules should emerge from repeated observed business patterns, not speculative abstraction.**<br />

Automation should not mean "send more messages."

It should mean that Rule & Form already knows the next useful action, knows when that action is no longer useful, and can execute it without the contractor remembering to do it manually.

Webhooks make Rule & Form responsive.

Provider Commands make external changes deliberate.

Neither guarantees that Rule & Form and a provider will remain in agreement forever.

Events can be missed. Provider resources can be edited manually. A command can succeed while its response disappears. Mappings can become invalid. Provider state can drift while Rule & Form is offline.

Reconciliation closes those gaps.

<br />\<Callout icon="terminal" color="#8B5CF6"\><br />  **For implementation** — synchronization is never a generic bidirectional merge. Every synchronized field or relationship has declared authority and direction. Projections are derived Rule & Form views. Reconciliation compares expected state with observable reality, classifies differences, and repairs only where ownership and retry safety are known.<br />\</Callout\><br />

## The boundary

```text
```

```text
                  Provider

            webhook ↓   ↑ command

                 Rule & Form
                      ↓
              canonical domain
              operational state
                      ↓
                 projections
                      ↓
            Business Hub / Ops

                 Rule & Form
                      ↕
               reconciliation
                      ↕
                  Provider
```

The paths serve different purposes.

| Path | Purpose |
| :-- | :-- |
| **Webhook** | Fast notification that something changed externally |
| **Provider Command** | Controlled intent for Rule & Form to change provider state |
| **Projection** | Local view optimized for Rule & Form product use |
| **Reconciliation** | Periodic or targeted proof that expected and actual state still agree |

**Fast paths provide responsiveness. Reconciliation provides convergence.**

## There is no generic sync

"Keep these systems in sync" is not an implementation rule.

For every piece of synchronized state, Rule & Form must know:

1. <br />what the field means,<br />
2. <br />who owns it,<br />
3. <br />which direction it may move,<br />
4. <br />what evidence establishes current reality,<br />
5. <br />what disagreement means,<br />
6. <br />whether automatic repair is safe.<br />

Example:

```text
```

```text
Business public phone

Authority:
Business Record

Direction:
Rule & Form → provider where required
```

Compare with:

```text
```

```text
SMS delivery state

Authority:
messaging provider

Direction:
provider → Rule & Form projection
```

And:

```text
```

```text
Lead identity

Authority:
Rule & Form

Provider representation:
HighLevel Opportunity

Direction:
Rule & Form identity → provider mapping
provider events → permitted operational updates
```

Those are three different synchronization contracts.

They should not be processed by one universal "merge records" function.

---

## Authority comes first

Reconciliation cannot decide what to repair until authority is known.

### Rule & Form authoritative

Examples may include:

```text
```

```text
Business identity
Business services
service areas
Rule & Form Lead identity
Site configuration
approved website content
automation policy
desired provider configuration
```

If provider reality disagrees with Rule & Form on a Rule & Form-owned field, provider state is drift.

### Provider authoritative

Examples may include:

```text
```

```text
message delivery result
provider resource existence
provider-generated timestamps
carrier registration state
external appointment execution state
```

Where the provider owns reality, Rule & Form updates its projection.

### Shared relationship, separate ownership

Some relationships include both.

Example:

```text
```

```text
Rule & Form Appointment
        ↓
Provider Mapping
        ↓
HighLevel Appointment
```

Rule & Form owns the Appointment identity.

The provider may own specific execution facts.

The synchronization contract defines which fields belong to each side.

### No last-write-wins

Avoid:

```text
```

```text
Rule & Form changed at 10:01

Provider changed at 10:02

        ↓

provider wins because newer
```

Time does not determine semantic authority.

Likewise:

```text
```

```text
newest timestamp wins
```

is not a tenancy or synchronization model.

**Authority beats recency.**

---

## Projections

A projection is a Rule & Form representation optimized for reading or product behavior.

Examples include:

```text
```

```text
Business Hub Lead list

Conversation summary

Appointment calendar view

Capability evidence

provider connection health

Home summary

integration status
```

The projection is derived from authoritative state.

```text
```

```text
domain state
        +
accepted provider facts
        ↓
projection
        ↓
product surface
```

### Projections are not canonical truth

If a projection becomes corrupt:

```text
```

```text
authoritative state
        ↓
rebuild
        ↓
projection restored
```

Do not require a staff member to edit the projection until it "looks right."

### A projection may be persisted

Persistence can be useful for:

```text
```

```text
fast Business Hub reads
aggregation
provider-backed normalized state
search
status summaries
```

Persisting the projection does not change its authority.

**Stored does not mean canonical.**

---

## Projection identity

Projections use Rule & Form identity.

Example:

```text
```

```text
Conversation Projection

conversation_id
customer_id
business_id

latest_message_at
unread_count
channel summary
```

Provider IDs may be included as supporting mapping information where necessary.

They do not become the projection's identity.

Avoid:

```text
```

```text
HighLevel Conversation ID
        ↓
becomes primary application identity
```

Prefer:

```text
```

```text
Rule & Form Conversation
        ↓
Provider Mapping
        ↓
HighLevel Conversation
```

---

## Projection updates

Projections change from committed Rule & Form facts.

Typical flow:

```text
```

```text
Provider Event
        ↓
normalized domain processing
        ↓
Message committed
        +
System Event
        ↓
Conversation projection updated
```

Or:

```text
```

```text
Lead state changed
        ↓
System Event
        ↓
Lead list projection updated
        ↓
Home summary updated
```

A UI projection should not normally parse raw provider payloads itself.

Provider vocabulary stops before the product projection layer.

---

## Projection updates are idempotent

A duplicate event must not produce duplicate projection effects.

Example:

```text
```

```text
message.received
event 123

processed twice

        ↓

Conversation unread count
must not increment twice
```

Projection handlers therefore use stable source identity or recomputation from authoritative state where appropriate.

### Prefer recomputation when simple

For small derived values:

```text
```

```text
new Lead count
```

it may be safer to calculate from current domain state than maintain a complicated incremental counter.

Use incremental projections when they materially improve performance or product behavior.

**Do not introduce consistency problems to avoid a query that was already cheap.**

---

## Webhooks are the fast path

Provider webhooks should update local state quickly.

```text
```

```text
provider
        ↓
webhook
        ↓
Provider Event
        ↓
domain processing
        ↓
projection
```

This allows the Business Hub to feel current without polling the provider on every page load.

But a webhook is not proof that all events were received.

```text
```

```text
provider changed
        ↓
webhook never arrives
        ↓
local state remains stale
```

That is why reconciliation exists.

---

## Command results are another fast path

When Rule & Form performs an external action:

```text
```

```text
Provider Command
        ↓
provider
        ↓
confirmed result
        ↓
mapping / transport / projection update
```

Rule & Form can update relevant local state immediately when the provider response provides trustworthy evidence.

Example:

```text
```

```text
create appointment
        ↓
provider confirms appointment ID
        ↓
Provider Mapping created
        ↓
Appointment projection updated
```

A later webhook may confirm the same state.

That duplicate evidence must be harmless.

---

## Command response and webhook can race

The same provider action may be observed through more than one path.

```text
```

```text
Rule & Form command

        ↓

Provider creates appointment

        ↙          ↘

API response      webhook

        ↘          ↙

      Rule & Form
```

The system must converge on one mapped Appointment.

It must not create two because two evidence paths arrived.

Stable Rule & Form identity and Provider Mapping make the two observations converge.

### Arrival order is not meaningful

The webhook may arrive:

```text
```

```text
before API response
```

or:

```text
```

```text
after API response
```

or not at all.

The synchronization contract must tolerate all three.

---

## Reconciliation

A reconciliation run compares Rule & Form's expected state with current observable provider state.

```text
```

```text
EXPECTED
Rule & Form state

        ↕

ACTUAL
provider state

        ↓

classification

MATCHED
DIVERGED
MISSING
UNEXPECTED
UNCERTAIN
UNRESOLVED
```

The exact stored status may be simpler.

The semantic distinctions remain important.

---

## Expected state

Expected state comes from the authority that owns the intended relationship.

Examples:

```text
```

```text
Customer
should have
HighLevel Contact mapping
```

```text
```

```text
SMS capability
should have
configured provider phone resource
```

```text
```

```text
Site
should have
assigned Framer project
```

```text
```

```text
Appointment
should have
provider appointment
```

Expected state is not whatever the provider happened to contain yesterday.

It comes from Rule & Form's current managed state.

---

## Actual state

Actual state is evidence obtained from the provider through its supported read surface.

Conceptually:

```text
```

```text
Provider Adapter

read resource
list relevant resources
retrieve current status
```

The adapter normalizes provider vocabulary before reconciliation logic evaluates it.

```text
```

```text
provider response
        ↓
adapter
        ↓
normalized actual state
        ↓
reconciler
```

Reconciliation logic should not contain provider HTTP response parsing scattered throughout domain code.

---

## Reconciliation scope

A reconciliation run has explicit scope.

Examples:

```text
```

```text
Integration Connection

Customer mapping

Conversation

Appointment

phone capability

Site publishing target
```

Conceptually:

```text
```

```text
Reconciliation Run

id

organization_id
business_id

integration_connection_id

scope_type
scope_id

started_at
completed_at

result
```

The exact schema may vary.

The important thing is that reconciliation is identifiable, tenant-scoped work.

---

## Targeted reconciliation

Targeted reconciliation resolves a known uncertainty or suspected drift.

Example:

```text
```

```text
Provider Command
uncertain

        ↓

reconcile specific provider resource

        ↓

found
    command succeeded

not found
    retry may be safe

cannot determine
    remain uncertain
```

This is particularly important after ambiguous provider outcomes.

Webhooks, Events & Command Queue owns the uncertain command state.

This page owns the comparison that resolves it.

---

## Scheduled reconciliation

Some provider relationships should also be checked periodically.

```text
```

```text
known managed resources
        ↓
scheduled reconciliation
        ↓
still present?
still mapped?
important state still consistent?
```

This catches:

- <br />missed webhooks<br />
- <br />provider-side manual edits<br />
- <br />deleted provider resources<br />
- <br />stale mappings<br />
- <br />failed provider updates<br />
- <br />credentials that stopped working<br />
- <br />provider state changed while Rule & Form was unavailable<br />

### Frequency follows risk

Not every object needs constant polling.

A phone or messaging capability may justify regular verification.

An immutable historical provider reference may not.

V1 chooses reconciliation cadence by:

```text
```

```text
customer impact
likelihood of drift
provider limits
cost
recovery requirements
```

Do not build continuous polling everywhere merely because reconciliation exists.

---

## Full reconciliation

A connection-level reconciliation may inspect the set of Rule & Form-managed provider resources.

Conceptually:

```text
```

```text
Integration Connection
        ↓
known Rule & Form mappings
        ↓
provider resources
        ↓
compare
```

This is useful for detecting:

```text
```

```text
mapping points to deleted resource

provider resource exists
but mapping missing

duplicate provider resource

managed configuration changed externally
```

A full reconciliation is heavier than targeted reconciliation.

It should not become the default response to every small uncertainty.

---

## One active reconciliation per scope

Two reconciliation jobs should not repair the same scoped relationship concurrently.

```text
```

```text
Connection A
Customer 123
        ↓
Reconciliation Run 1
active

Reconciliation Run 2
        ↓
wait / coalesce
```

The exact implementation may use run uniqueness, leases, or workflow concurrency.

The architectural rule is simpler:

**do not let concurrent repair processes fight over the same provider state.**

Unrelated scopes continue independently.

---

## Divergence classes

Differences should be classified before repair.

### Matched

```text
```

```text
expected
        =
actual
```

No repair needed.

### Missing externally

Rule & Form expects a provider representation but it does not exist.

```text
```

```text
Customer
has mapping intent

Provider Contact
missing
```

Possible causes:

```text
```

```text
manual deletion
failed creation
provider data loss
stale mapping
```

### Missing locally

Provider contains a relevant managed resource that Rule & Form cannot map.

```text
```

```text
provider resource exists

Rule & Form mapping absent
```

This is not permission to attach it to whichever Customer looks similar.

Identity must be proven.

### Value divergence

The resource exists but a managed field differs.

```text
```

```text
Expected forwarding number
325-555-0101

Actual
325-555-0199
```

Repair depends on authority.

### Duplicate provider representation

More than one provider resource appears to represent one Rule & Form object.

```text
```

```text
Customer 123

        ↓

Contact A
Contact B
```

Automatic destructive merge may be unsafe.

### Mapping invalid

The stored provider identifier no longer identifies the expected object.

### Unknown

The provider could not be queried or returned insufficient evidence.

```text
```

```text
provider unavailable
permission denied
rate limited
ambiguous response
```

Unknown is not divergence.

**Failure to observe reality is not proof that reality is wrong.**

---

## Automatic repair

Automatic repair is allowed only when three conditions hold:

1. <br />Rule & Form clearly owns the desired state.<br />
2. <br />Provider identity is known.<br />
3. <br />The repair is safely repeatable.<br />

Example:

```text
```

```text
Rule & Form authoritative:
forwarding destination

provider value drifted

mapping valid

        ↓

create Provider Command
restore expected value
```

The reconciler does not call the provider directly.

It creates or requests the same durable provider intent used elsewhere.

```text
```

```text
reconciliation
        ↓
repair decision
        ↓
Provider Command
        ↓
standard execution path
```

This preserves:

- <br />idempotency<br />
- <br />retry behavior<br />
- <br />audit history<br />
- <br />provider abstraction<br />
- <br />uncertain-result handling<br />

---

## Reconciliation does not bypass commands

Avoid:

```text
```

```text
reconciler
        ↓
provider API
        ↓
mutate directly
```

for managed provider side effects.

Prefer:

```text
```

```text
reconciler
        ↓
difference classified
        ↓
Provider Command
        ↓
adapter
        ↓
provider
```

Reconciliation decides **what needs repair**.

Provider Commands own **the durable external mutation**.

---

## Provider-authoritative repair

Where provider reality owns the field:

```text
```

```text
provider state
        ↓
accepted normalized fact
        ↓
Rule & Form projection updated
```

Example:

```text
```

```text
Message delivery

Rule & Form:
sent

Provider:
delivered

        ↓

Rule & Form transport projection:
delivered
```

No outbound repair is appropriate.

The provider owns that result.

### Authority limits the update

Provider-authoritative reconciliation may update:

```text
```

```text
message transport state
```

without gaining authority over:

```text
```

```text
Lead source
Business public phone
Customer identity
Business Record
```

**Reconciliation does not broaden provider authority.**

---

## Human review

Some divergence cannot be repaired automatically.

Examples include:

- <br />ambiguous Customer mapping<br />
- <br />duplicate external Contacts<br />
- <br />conflicting provider identity<br />
- <br />provider resource modified in a way that may reflect intentional human action<br />
- <br />unsupported provider state<br />
- <br />destructive repair<br />
- <br />missing data required to prove ownership<br />

Those become visible operating state.

```text
```

```text
DIVERGENCE

requires review

reason
ambiguous provider mapping
```

Workbench exposes the evidence.

Internal Operations owns the corrective action.

---

## Manual provider edits

Early Rule & Form operations may involve legitimate manual provider setup.

That does not mean all later manual provider edits are authoritative.

A manually created resource can become managed Rule & Form infrastructure once its mapping and expected configuration are recorded.

```text
```

```text
manual setup
        ↓
Provider Mapping recorded
        ↓
expected state recorded
        ↓
managed relationship
```

Later divergence is evaluated against that contract.

### Manual is allowed; invisible is not

Avoid:

```text
```

```text
staff configures HighLevel
        ↓
nothing recorded locally
        ↓
works until nobody remembers why
```

Prefer:

```text
```

```text
staff configures provider
        ↓
Rule & Form records connection
mapping
required configuration
        ↓
reconciliation can inspect it
```

The system does not need to automate every first setup step.

It does need to know what setup exists.

---

## External edits can be classified

A provider resource may be changed manually after Rule & Form starts managing it.

Possible responses include:

```text
```

```text
adopt
repair
ignore
review
```

The response depends on field authority.

### Repair

Rule & Form owns the value.

Provider drift is accidental or unsupported.

### Adopt

The provider owns the value and Rule & Form should project the new reality.

### Ignore

The provider field is outside Rule & Form's managed surface.

### Review

Ownership or intent cannot be safely determined.

There is no generic rule:

```text
```

```text
provider changed
        ↓
overwrite Rule & Form
```

and no generic inverse:

```text
```

```text
provider changed
        ↓
always overwrite provider
```

---

## Provider fields outside the managed surface

Providers contain far more state than Rule & Form needs.

HighLevel may expose fields, tags, pipelines, settings, automations, and account data unrelated to the Rule & Form product.

Framer projects may contain provider-side implementation detail irrelevant to Rule & Form's semantic model.

Reconciliation should inspect only the state Rule & Form actually manages or relies on.

```text
```

```text
managed provider surface
        ↓
reconcile

everything else
        ↓
ignore unless it affects a managed dependency
```

This reduces accidental coupling.

**Do not turn reconciliation into provider cloning.**

---

## Provider Mappings

Mappings are central reconciliation anchors.

```text
```

```text
Rule & Form object
        ↓
Provider Mapping
        ↓
provider object
```

A valid mapping should allow Rule & Form to answer:

```text
```

```text
which provider object represents this?

which Rule & Form object does this provider ID belong to?

which Integration Connection owns the relationship?
```

### Mapping verification

Reconciliation can verify:

```text
```

```text
provider object still exists

provider object type still matches

provider resource still belongs to expected connection

identity is not duplicated
```

A mapping is not assumed valid forever merely because it once worked.

---

## Missing mappings

A provider event or reconciliation result may expose a provider object for which Rule & Form has no mapping.

Do not immediately match by:

```text
```

```text
name
phone
email
display label
```

unless the specific subsystem defines that as a safe deterministic recovery rule.

For Customer identity, conservative matching rules from Lead, Customer & Job Model still apply.

For other provider resources, the owning integration defines its recovery strategy.

### Discovery is not authority

Finding a provider resource that looks similar does not prove it represents the same Rule & Form object.

---

## Out-of-order events

A late webhook can arrive after reconciliation already observed newer provider state.

```text
```

```text
Provider state v5
        ↓
reconciliation
        ↓
Rule & Form projection v5

later

old webhook
provider state v4
        ↓
arrives
```

The old event must not blindly regress the projection.

Where the provider supplies:

```text
```

```text
revision
sequence
occurred_at
updated_at
```

the adapter uses trustworthy ordering evidence.

Where ordering cannot be proven, current provider reconciliation outranks unsafe assumptions about webhook arrival order.

Webhooks, Events & Command Queue owns the inbound event model.

---

## Deletions

External deletion needs explicit semantics.

Example:

```text
```

```text
mapped provider Contact deleted
```

That does not imply:

```text
```

```text
delete Rule & Form Customer
```

The Customer remains a Rule & Form object.

Possible result:

```text
```

```text
Provider Mapping
invalid / missing

Customer
unchanged

Capability or synchronization state
degraded where relevant
```

Rule & Form may recreate the provider representation if safe and required.

### Provider deletion never cascades blindly into canonical identity

This applies broadly:

```text
```

```text
HighLevel Contact deleted
        ≠
delete Customer

Framer project deleted
        ≠
delete Site

provider appointment deleted
        ≠
delete all Customer history
```

Provider lifecycle and Rule & Form lifecycle remain separate.

---

## Local deletions

When Rule & Form intentionally removes managed desired state, reconciliation must distinguish that from drift.

Example:

```text
```

```text
Service no longer offered
        ↓
new desired website state
        ↓
provider CMS item no longer desired
```

Publishing owns convergence of the website provider state.

The reconciler should not later interpret intentional removal as:

```text
```

```text
missing provider item
        ↓
recreate it
```

Expected state must be based on current Rule & Form intent.

**Reconciliation repairs toward current desired state, not historical existence.**

---

## Tombstones and historical mappings

Some removed mappings may need historical evidence.

For example:

```text
```

```text
Customer mapped to Contact abc123

provider Contact later replaced
```

Workbench may still need to explain historical Provider Events or Command Attempts that referenced `abc123`.

V1 may retain mapping history or audit evidence without treating the old mapping as active.

The physical representation may use:

```text
```

```text
inactive mapping
superseded mapping
historical mapping record
```

depending on implementation.

Do not destroy provenance merely to keep the active mapping table aesthetically simple.

---

## Freshness

Provider-backed projections need an understandable freshness model.

Useful evidence may include:

```text
```

```text
last provider event

last successful reconciliation

last failed reconciliation

provider connection state
```

This allows Rule & Form to distinguish:

```text
```

```text
current
stale
unknown
```

where the product genuinely needs that distinction.

### Stale is not necessarily wrong

A projection may be:

```text
```

```text
last reconciled 5 minutes ago
```

and still be correct.

Freshness describes evidence age.

It does not automatically declare the value false.

### Critical state may degrade

For a capability that depends on current provider evidence:

```text
```

```text
provider connection cannot be verified
for an unacceptable period
```

Capability State may stop confidently reporting `Live`.

The capability resolver owns that translation.

Reconciliation provides the evidence.

---

## Capability State consumes reconciliation evidence

Capability State should not perform arbitrary provider polling itself.

Prefer:

```text
```

```text
Provider Events
        +
Reconciliation
        ↓
normalized provider evidence
        ↓
Capability Resolver
        ↓
Live / Ready / Action needed / ...
```

This separates:

```text
```

```text
What does the provider currently appear to be doing?
```

from:

```text
```

```text
What does that mean to the customer?
```

Capability & Provisioning State owns the second question.

---

## Business Hub consumes projections

Business Hub should normally read:

```text
```

```text
Rule & Form projections
```

rather than perform:

```text
```

```text
live provider query
```

for every screen.

This gives the product:

- <br />stable tenant-scoped reads<br />
- <br />predictable latency<br />
- <br />provider resilience<br />
- <br />cross-provider composition<br />
- <br />inspectable history<br />
- <br />one Rule & Form vocabulary<br />

Example:

```text
```

```text
Inbox
        ↓
Conversation projection

Schedule
        ↓
Appointment projection

Home
        ↓
Lead / Conversation / Appointment summaries
```

Reconciliation keeps those views trustworthy over time.

---

## Rebuilding projections

A projection should be rebuildable from its authoritative sources where practical.

Example:

```text
```

```text
Conversation summary corrupted
        ↓
Conversation + Messages
        ↓
rebuild projection
```

or:

```text
```

```text
Home lead count incorrect
        ↓
Lead state
        ↓
recompute
```

The system should know the difference between:

```text
```

```text
repair projection
```

and:

```text
```

```text
repair provider divergence
```

Those are separate operations.

### Projection rebuild should not call providers unnecessarily

If the authoritative Rule & Form state already contains what the projection needs:

```text
```

```text
rebuild locally
```

Do not turn every projection repair into a provider reconciliation.

---

## Reconciliation runs are durable

A reconciliation run should survive request boundaries and provider delays.

```text
```

```text
Reconciliation Run
        ↓
load expected state
        ↓
read provider
        ↓
compare
        ↓
classify
        ↓
repair decision
        ↓
complete
```

For heavier reconciliation, Inngest may orchestrate execution.

The database retains enough state to know:

```text
```

```text
what was checked

when

what differed

what action resulted
```

---

## Reconciliation does not hold long database transactions

Provider calls happen outside open database transactions.

Avoid:

```text
```

```text
BEGIN

load expected state

call provider
wait 4 seconds

compare

write

COMMIT
```

Prefer:

```text
```

```text
load / snapshot required local state
        ↓
commit / release database work
        ↓
call provider
        ↓
open new transaction
        ↓
verify local assumptions still valid
        ↓
apply reconciliation result
```

This prevents slow external APIs from holding database resources and avoids pretending provider calls are part of one atomic database transaction.

---

## State can change during reconciliation

Suppose reconciliation begins with:

```text
```

```text
expected phone
325-555-0101
```

while the customer changes it to:

```text
```

```text
325-555-0202
```

before the provider read finishes.

The reconciliation result must not "repair" the provider back to stale desired state.

Before creating a repair command, compare against current authoritative state or the expected-state version used by the run.

```text
```

```text
reconciliation started from version 12

current desired version now 13

        ↓

stale reconciliation result
        ↓
discard / reevaluate
```

**Reconciliation never gains permission to overwrite newer Rule & Form intent.**

---

## Repair commands are version-aware

Where desired state has versions, repair identity may include the desired version.

Example:

```text
```

```text
sync-customer:{customer_id}:{desired_version}
```

or equivalent stable intent.

This prevents an old repair attempt from masquerading as the current desired operation.

Exact idempotency encoding belongs in [Naming, IDs & Conventions](/architecture/foundation/naming-ids-and-conventions).

---

## Reconciliation after uncertain commands

An uncertain Provider Command is one of the highest-value reconciliation cases.

```text
```

```text
Command
send message

provider may have accepted it

response lost

        ↓

UNCERTAIN
```

The reconciler attempts to establish:

```text
```

```text
Did the provider create / accept
the intended side effect?
```

Possible outcomes:

### Confirmed success

```text
```

```text
provider evidence found
        ↓
Command succeeded
        ↓
mapping / projection updated
```

### Confirmed absent

```text
```

```text
provider proves action absent
        ↓
retry may become safe
```

### Still ambiguous

```text
```

```text
insufficient evidence
        ↓
Command remains uncertain
        ↓
human review or later reconciliation
```

There is no fourth outcome:

```text
```

```text
shrug
        ↓
send it again anyway
```

---

## Repair loops

Automatic reconciliation must not create infinite correction loops.

Example:

```text
```

```text
Rule & Form repairs provider
        ↓
provider emits webhook
        ↓
Rule & Form interprets webhook
as conflicting new intent
        ↓
repairs again
```

Authority and mapping prevent this.

A provider event that merely reports the state Rule & Form just established should converge without generating contradictory new desired state.

### Cause and correlation help

Where available:

```text
```

```text

        ↓
provider result
        ↓
Provider Event
```

correlation can help explain that the event is confirmation of known execution.

Correctness should not depend solely on correlation being present.

The current authority and normalized state must still converge.

## Rate limits

Reconciliation must respect provider limits.

A provider outage should not cause:

```text
```

```text
10,000 reconciliation requests
every minute
```

because every customer capability noticed stale evidence.

Use:

```text
```

```text
scoped scheduling
backoff
provider-aware concurrency
targeted reconciliation
```

according to operational need.

Provider rate-limit behavior remains inside the adapter/execution infrastructure.

```text
```

```text

        ↓

```

V1 should favor connection-level failure containment where provider behavior supports it.



Capability State can then reflect the affected customer-facing consequences.

## Reconciliation and retries are different

Retry means:

**try the same intended external operation again when safe.**

Reconciliation means:

**inspect current reality and determine what is true.**

```text
```

```text
retry
        ≠
reconcile
```

An uncertain command needs reconciliation before retry.

A rate-limited command may need only retry.

A manually deleted provider resource may require reconciliation and then a new repair command.

The distinction should remain explicit.

---

## Reconciliation and replay are different

Replay means:

**process an existing durable event again.**

Reconciliation means:

**read current provider reality.**

Example:

```text
```

```text
Provider Event processing bug
        ↓
fix code
        ↓
replay same Provider Event
```

versus:

```text
```

```text
suspect missed provider change
        ↓
query provider
        ↓
reconcile current state
```

Do not use event replay to pretend historical events necessarily describe current provider reality.

---

## Reconciliation and migration are different

If Rule & Form deliberately changes provider representation:

```text
```

```text
new template version
new provider account
new phone resource
provider migration
```

that is an explicit migration or provisioning operation.

Reconciliation can verify the resulting state.

It should not secretly perform product migrations because the old and new states differ.

## Acceptance conditions

Sync, Projections & Reconciliation is working when:

- <br />Every synchronized field or relationship has a declared authority and direction.<br />
- <br />Provider recency cannot override Rule & Form-owned state merely because its timestamp is newer.<br />
- <br />A Business Hub projection can be rebuilt without treating the projection itself as canonical state.<br />
- <br />Processing the same source fact twice does not double-apply projection changes.<br />
- <br />Normal Business Hub reads do not require live provider calls.<br />
- <br />A provider webhook can update local normalized state without leaking provider vocabulary into product projections.<br />
- <br />A command response and webhook describing the same provider resource converge on one Rule & Form object.<br />
- <br />Webhook arrival before or after the command response does not create duplicate mappings.<br />
- <br />A missed webhook can be corrected by later reconciliation.<br />
- <br />A manually deleted provider resource can be detected.<br />
- <br />A stale Provider Mapping can be identified.<br />
- <br />An unexpected provider resource is not automatically attached to a customer based on weak identity.<br />
- <br />Provider-owned state can update its Rule & Form projection without gaining authority over unrelated fields.<br />
- <br />Rule & Form-owned provider drift can generate a repair command.<br />
- <br />Reconciliation never mutates the provider directly outside the Provider Command path.<br />
- <br />An ambiguous divergence can stop for human review rather than forcing an unsafe merge or repair.<br />
- <br />One reconciliation run cannot overwrite newer Rule & Form desired state discovered after the run began.<br />
- <br />Two active reconciliation processes do not fight over the same scoped relationship.<br />
- <br />An uncertain Provider Command is reconciled before an unsafe retry.<br />
- <br />Reconciliation can mark an uncertain command succeeded when provider evidence proves the action occurred.<br />
- <br />Reconciliation can determine retry is safe when provider evidence proves the action did not occur.<br />
- <br />Lack of provider evidence does not falsely become `failed` or `missing`.<br />
- <br />Provider deletion does not automatically delete Rule & Form canonical identity.<br />
- <br />Current desired state prevents reconciliation from recreating intentionally removed provider state.<br />
- <br />A broken Integration Connection blocks dependent reconciliation rather than producing uncontrolled child retries.<br />
- <br />Capability State can consume freshness and provider evidence without implementing its own provider synchronization logic.<br />
- <br />Workbench can display expected state, actual state, authority, divergence, and resolution.<br />
- <br />Demo reconciliation uses the same architecture without reaching production provider resources.<br />

## Foundation rules

1. **There is no generic bidirectional sync.**<br />
2. **Every synchronized field and relationship has declared authority and direction.**<br />
3. **Authority outranks timestamp recency.**<br />
4. **Rule & Form-owned state is not overwritten merely because a provider changed later.**<br />
5. **Provider-owned facts update only the Rule & Form projections they are authorized to define.**<br />
6. **Projections optimize reading. They do not become new sources of truth.**<br />
7. **Persisted projections remain rebuildable where practical.**<br />
8. **Duplicate events and duplicate evidence must be harmless.**<br />
9. **Webhooks are the fast inbound path, not the sole guarantee of convergence.**<br />
10. **Provider Command results are useful evidence, but later reconciliation still protects against drift.**<br />
11. **A command response and webhook may race without creating duplicate domain identity.**<br />
12. **Reconciliation compares expected Rule & Form state with observable provider reality.**<br />
13. **Reconciliation is explicitly tenant-scoped.**<br />
14. **Unknown provider state is not automatically classified as divergence.**<br />
15. **Missing provider state does not delete Rule & Form identity.**<br />
16. **Unexpected provider resources are not attached through weak matching merely to make reconciliation pass.**<br />
17. **Automatic repair requires known authority, known identity, and safe repeatability.**<br />
18. **External repair executes through Provider Commands rather than a hidden reconciliation mutation path.**<br />
19. **Provider-authoritative reconciliation updates normalized Rule & Form state without broadening provider authority.**<br />
20. **Ambiguous or destructive repair stops for review.**<br />
21. **Manual early provisioning is allowed. Unrecorded provider configuration is not.**<br />
22. **Reconciliation inspects only the provider surface Rule & Form manages or depends on.**<br />
23. **Provider Mappings are verified rather than assumed valid forever.**<br />
24. **Late provider events cannot blindly regress newer known state.**<br />
25. **Reconciliation repairs toward current desired state, not historical existence.**<br />
26. **Freshness describes the age of evidence, not automatic truth or falsity.**<br />
27. **Capability State consumes reconciliation evidence rather than becoming another synchronization engine.**<br />
28. **A stale reconciliation result cannot overwrite newer authoritative Rule & Form intent.**<br />
29. **Uncertain external execution is reconciled before unsafe retry.**<br />
30. **Retry, replay, reconciliation, and migration remain distinct operations.**<br />
31. **A broken root Integration Connection should contain failure rather than trigger uncontrolled child work.**<br />
32. **Repair loops are prevented through explicit authority and convergent state handling.**<br />
33. **Workbench exposes expected, actual, authority, and resolution.**<br />
34. **The demo uses the same reconciliation model as production.**<br />
35. **V1 implements only reconciliation required by the first real provider-backed product loop.**<br />

Rule & Form does not need every provider to be perfect.

It needs a reliable way to notice when reality drifted, decide which side is authoritative, and return the system to a known state without guessing.

**Observe reality. Respect authority. Repair only what is safe. Converge.**
