Rule & Form is a TypeScript application built on MakerKit Lite and Supabase.

The starter kit supplies commodity SaaS infrastructure. Rule & Form owns the domain model, Business Record, Vertical Blueprints, structured intake, website system, operational state, provider boundaries, and the rules that make the product distinct.

The distinction is deliberate.

 \<Callout icon="terminal" color="#8B5CF6"\> **For implementation** - V1 starts from MakerKit Lite's existing Next.js \+ Supabase conventions. Do not replace its working authentication, project structure, Supabase setup, or UI foundation because another library is preferred in isolation. Extend the existing repository around Rule & Form's domain boundaries. The Build Spec defines ownership and invariants; the repository defines the implementation that actually exists. \</Callout\>

## Data-access boundary

Application code does not treat the Supabase client as permission to query tenant-owned tables from anywhere.

The expected path is:

```text
```

```text
application surface
        ↓
domain operation
        ↓
authorized Organization context
        ↓
Rule & Form data-access boundary
        ↓
Supabase / PostgreSQL
```

Page components should not become the authoritative location for tenant queries or business rules.

Provider code should not reach around the domain layer because calling the database directly is easier.

The exact repository functions and package structure may evolve.

The boundary does not:

**tenant context and domain rules reach the database before customer data does.**

## Tenant containment uses two layers

V1 uses both explicit Rule & Form tenant scoping and PostgreSQL Row Level Security.

They solve related but different failure modes.

```text
```

```text
Authenticated customer request

Supabase Auth
        ↓
User

Rule & Form authorization
        ↓
Organization

explicit Organization-scoped operation
        +
PostgreSQL RLS

        ↓

tenant-owned rows
```

Customer-accessible tenant tables enable appropriate RLS policies.

The application also carries explicit Organization identity through its domain and data-access paths.

**RLS is a containment boundary. It does not remove tenant awareness from application code.**

### Why explicit Organization scope remains mandatory

Rule & Form also has trusted server operations without an interactive customer session:

```text
```

```text
webhooks
background jobs
publishing
provider commands
reconciliation
internal operations
controlled migrations
```

Some of those operations may legitimately use privileged database access.

Privileged Supabase credentials can bypass ordinary RLS enforcement.

Therefore:

```text
```

```text
privileged server operation
        ↓
trusted tenant resolution
        ↓
explicit Organization
        ↓
Business where applicable
        ↓
scoped domain operation
        ↓
privileged data access
```

A privileged credential is **not** tenant context.

Knowing a Business ID is **not** tenant context.

Receiving a provider object ID is **not** tenant context.

The application resolves the owner before touching tenant-owned state.

<br />\<Callout icon="lock" color="#E2E8F0"\><br />  Customer paths use database containment and explicit application scope. Privileged paths may bypass RLS technically, but they never bypass Rule & Form tenant resolution architecturally.<br />\</Callout\><br />

## Privileged Supabase access

Privileged database access has a narrow server-only boundary.

It is appropriate for operations that genuinely cannot execute under a customer session, such as:

```text
```

```text
verified provider webhook processing
controlled background work
system reconciliation
internal administration
selected provisioning operations
```

It is not the default client for ordinary application code.

Do not build:

```text
```

```text
everything
    ↓
service / secret credential
    ↓
all rows accessible
    ↓
remember to filter correctly
```

Prefer:

```text
```

```text
customer operation
    ↓
customer-scoped client + RLS


privileged system operation
    ↓
narrow server boundary
    ↓
explicit Organization scope
    ↓
privileged client only where required
```

Privileged keys never reach the browser, logs, client bundles, screenshots, or public configuration.

## No ORM requirement in V1

Drizzle is not a V1 architectural dependency.

MakerKit Lite already supplies a Supabase/PostgreSQL path and migration structure suitable for beginning the application.

Rule & Form should not insert another data abstraction before a real requirement justifies it.

```text
```

```text
V1

Supabase
    ↓
PostgreSQL
    ↓
Rule & Form data-access boundary
```

If later implementation evidence shows that Drizzle materially improves complex typed querying, schema management, or developer safety, it may be introduced behind the existing boundary.

```text
```

```text
future

Rule & Form domain
        ↓
data-access boundary
        ↓
Drizzle if useful
        ↓
Supabase PostgreSQL
```

That would be an implementation change.

It must not become a Business Record, tenancy, or provider-architecture change.

**Do not add infrastructure because we might want it later.**

## Database migrations

Database structure changes through version-controlled Supabase/PostgreSQL migrations.

```text
```

```text
schema requirement
        ↓
SQL migration
        ↓
local validation
        ↓
non-production validation
        ↓
merge with application change
        ↓
production application
```

A database change must be reproducible from repository history.

Production schema is not maintained through undocumented dashboard edits.

### Forward-compatible releases

Application code and database state do not deploy atomically.

Where adjacent deployments could encounter different schema states, use an expand-contract sequence.

<br />\<Steps\><br />  \<Step title="Expand"\><br />    Add new compatible database structure.<br />  \</Step\><br />  \<Step title="Support both states"\><br />    Deploy application code that can operate safely during transition.<br />  \</Step\><br />  \<Step title="Move"\><br />    Backfill or migrate data and behavior.<br />  \</Step\><br />  \<Step title="Contract"\><br />    Remove obsolete structure in a later controlled release.<br />  \</Step\><br />\</Steps\><br />

Application rollback never assumes the database also rolled back.

---

## Row Level Security changes with the schema

RLS policy changes are database changes.

They belong in the same version-controlled migration history as the tables they protect.

Do not configure a production tenant policy manually in a dashboard and leave no repository record of it.

A tenant-owned table is not considered complete merely because its columns exist.

Its access model must also exist.

```text
```

```text
tenant-owned table

schema
+
foreign-key ownership
+
indexes where required
+
RLS policy where exposed
+
application scoped access
```

Tenant-isolation tests verify the resulting behavior.

Accounts, Tenancy & Identity owns the authority rules.

Security, Permissions & Secrets owns the broader security policy.

## Environments

Rule & Form uses three environment classes in V1.

<br />\<Tabs\><br />  \<Tab title="Local"\><br />    Runs the MakerKit application and local Supabase development stack.<br />

```text
```

```text
Data is synthetic or development-only.

Local state may be seeded, reset, corrupted, regenerated, and deleted.

Customer provider credentials are absent by default.

Provider behavior may use sandbox resources, dedicated developer resources, fixtures, or controlled simulation.
```

<br />  \</Tab\><br />  \<Tab title="Preview"\><br />    Runs branch code in a hosted non-production environment.<br />

```text
```

```text
Uses non-production application data and non-production provider configuration.

A preview cannot publish over a customer website, send through a production customer messaging resource, mutate production Business Records, or execute against production provider credentials.
```

<br />  \</Tab\><br />  \<Tab title="Production"\><br />    Runs code merged to `main`.<br />

```text
```

```text
Contains real customer data and approved production provider connections.

Only production-scoped credentials exist here.

Production actions use the full authorization, tenant, validation, command, audit, and observability boundaries defined by the Build Spec.
```

<br />  \</Tab\><br />\</Tabs\><br />

A permanent fourth staging environment is deferred until real operating conditions justify maintaining one. \<Badge color="orange" size="sm" stroke\>Deferred\</Badge\>

### Environment boundaries matter more than names

The invariant is:

```text
```

```text
non-production
        ↓
cannot affect
        ↓
customer production
```

A variable named `PREVIEW=true` is not itself protection.

The actual credentials, database project, publishing targets, phone resources, provider mappings, and permissions must enforce the separation.

## Background execution

Long-running work does not depend on the browser request that started it.

```text
```

```text
user action
        ↓
durable local state
        ↓
workflow trigger
        ↓
Inngest
        ↓
durable steps
        ↓
provider work
```

Closing the browser does not cancel a Publishing Run.

A Vercel request ending does not erase Provider Command intent.

A deployment occurring during long-running work does not redefine the domain state being processed.

Webhooks, Events & Command Queue owns durable external intent.

Workflow & Orchestration Engine owns multi-step execution.

### Inngest does not become the source of truth

Inngest executes and resumes work.

Rule & Form PostgreSQL owns the durable domain state required to explain that work.

```text
```

```text
database
    owns intent and domain truth

Inngest
    owns workflow execution
```

If an execution mechanism is replaced later, the Business Record, Provider Commands, Publishing Runs, and other Rule & Form objects do not disappear with it.

## Secrets and configuration

Configuration is environment-scoped and schema-validated.

| Rule | Applies to |
| :-- | :-- |
| Secrets never live in source code | All environments |
| Local secrets remain in ignored local configuration | Local |
| Server-only credentials never reach the browser | All environments |
| Production credentials never enter Preview | Preview |
| Provider tokens never appear in logs | All environments |
| Privileged Supabase credentials remain server-only | All environments |
| Required configuration is validated before dependent work begins | All environments |

Not every integration credential needs to exist on day one.

Configuration should be required when the corresponding product capability is introduced.

Avoid turning an unused future provider into a startup dependency.

### Customer-facing Supabase access

Only client-safe Supabase configuration may reach browser code.

Privileged credentials remain behind explicit server boundaries.

The application does not assume that hiding a value in a JavaScript variable provides security.


## Acceptance conditions

Stack, Repo & Environments is correctly implemented when:

- <br />A clean MakerKit Lite checkout can become the Rule & Form repository without rebuilding authentication from scratch.<br />
- <br />A real User can authenticate through Supabase Auth and reach only authorized application routes.<br />
- <br />Rule & Form can represent User → Membership → Organization → Business without requiring customer team-management UI.<br />
- <br />Tenant-owned customer access is constrained by explicit Organization scope and applicable RLS policy.<br />
- <br />Tenant A cannot read or modify Tenant B data by changing an object identifier.<br />
- <br />Privileged server code cannot operate on tenant-owned data without resolving explicit tenant context.<br />
- <br />Privileged Supabase credentials never appear in browser code.<br />
- <br />Database schema and RLS policy changes are reproducible from repository migrations.<br />
- <br />A branch preview cannot reach production customer provider resources.<br />
- <br />The public demo cannot reach real customer data or production customer provider resources.<br />
- <br />A background workflow can continue after the initiating browser request ends.<br />
- <br />Rule & Form durable domain state remains in PostgreSQL rather than existing only inside the workflow provider.<br />
- <br />Stored assets have Rule & Form identity independent from temporary storage URLs.<br />
- <br />An implementation agent can locate the governing Build Spec page without treating the Build Spec as replacement for repository inspection.<br />
- <br />Drizzle can be added later without changing the Rule & Form domain contract if a real need emerges.<br />
- <br />A future SaaS-shell migration can occur without redefining Business Record, Website Engine, provider identity, or publication provenance.<br />

## Foundation rules

1. **MakerKit Lite is the V1 application foundation, not disposable demo code.**<br />
2. **Supabase Auth owns authentication mechanics. Rule & Form owns authorization and tenant meaning.**<br />
3. **Organization remains the Rule & Form tenant boundary.**<br />
4. **Customer-scoped access uses both explicit Organization scope and applicable PostgreSQL RLS.**<br />
5. **RLS strengthens tenant containment. It does not remove tenant scope from application code.**<br />
6. **Privileged database access is server-only, narrow, and always paired with trusted tenant resolution.**<br />
7. **A privileged credential is never tenant authority.**<br />
8. **Supabase PostgreSQL stores Rule & Form state. Supabase does not define Rule & Form domain identity.**<br />
9. **V1 does not require an ORM.**<br />
10. **Database and RLS changes are version-controlled migrations.**<br />
11. **Business rules do not belong primarily in page components.**<br />
12. **Provider-specific behavior stays behind integration boundaries.**<br />
13. **Repository conventions are preserved unless a product requirement justifies changing them.**<br />
14. **GitHub is the canonical source of application code and schema history.**<br />
15. `main `**represents production application code.**<br />
16. **Non-production environments cannot affect production customer systems.**<br />
17. **The public demo uses real application paths with synthetic tenant state.**<br />
18. **Inngest executes durable workflows; PostgreSQL retains the domain state that explains them.**<br />
19. **Supabase Storage is a V1 implementation behind Rule & Form Asset identity.**<br />
20. **Secrets are environment-scoped and privileged credentials remain server-only.**<br />
21. **Infrastructure is introduced when the build sequence requires it, not because it may be useful someday.**<br />
22. **MakerKit Pro is a possible future shell migration, not a V1 dependency.**<br />
23. **Development tools may change without changing the repository or architecture source of truth.**<br />
24. **The Build Spec defines intent and invariants. The repository defines current implementation. Conflicts are surfaced, not hidden.**<br />

The starting stack should remove commodity work without deciding what Rule & Form becomes.

**Use the foundation. Own the domain. Keep the boundary.**
