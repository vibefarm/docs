# Stack, Repo & Environments

Rule & Form is a TypeScript application built on managed infrastructure.

The product-specific work lives in our domain model, Business Record, intake, rendering, publishing, provisioning, operational logic, Workbench, and provider interfaces.

Generic infrastructure stays generic.

> **For implementation:** this page defines architectural constraints and current platform choices. It does not prescribe exact file structure, helper functions, or implementation patterns unless stated as a rule. Inspect the current repository and linked specifications before changing working conventions.

## Application stack

| Layer | Choice | Role |
| --- | --- | --- |
| Application | Next.js · React · TypeScript | Portal, intake, Workbench, internal tools, APIs |
| Database | PostgreSQL | Canonical application data |
| Data access | Drizzle ORM | Schema, migrations, typed database access |
| Authentication | Better Auth | Authentication, sessions, account membership |
| Validation | Zod | Runtime, configuration, and schema validation |
| Background work | Inngest | Durable workflows, retries, scheduled work |
| Hosting | Vercel | Application hosting and preview deployments |
| Source control | GitHub | Canonical repository and history |
| File storage | S3-compatible object storage | Photos, uploads, and generated assets |
| Email | Resend | Transactional application email |
| Observability | Sentry · structured logs · workflow history | Application errors, system activity, asynchronous execution |

The storage provider is deliberately not part of the architecture. The application depends on the storage contract, not a specific vendor.

PostgreSQL is the database contract. The database host can change without changing the domain model.

## Ownership boundary

Commodity application infrastructure includes authentication, sessions, account membership, storage, transactional email, deployment, error reporting, and UI primitives.

Rule & Form owns the systems that contain Rule & Form knowledge:

Business Record · trade schemas · structured intake · content state · rendering rules · template mappings · publishing · provisioning · operational domain · Workbench · provider adapters · audit history · contractor-facing product logic.

That boundary matters more than the vendor underneath any individual layer.

## Repository

There is one canonical application repository.

The application is organized around clear ownership boundaries:

```text
Application surfaces
Domain
Database
Business Record
Intake
Content
Publishing
Provisioning
Integrations
Validation
Shared UI
```

These are logical boundaries, not mandatory folder names.

Agents should preserve the repository's working structure unless a change is required to enforce one of these boundaries.

Business rules do not belong in page components.

Provider-specific behavior does not leak across the application.

Database access does not bypass the established data-access boundary for convenience.

## Repository rules

`main` is production.

Work happens on short-lived branches.

A branch represents one coherent change.

Every meaningful branch is deployed to a preview environment before production merge.

Git is the source of truth for application code, migrations, schemas, configuration, and implementation history.

Production-only fixes do not exist outside the repository.

## Merge gate

A change is not ready because it works in one browser session.

Repository CI must verify the checks appropriate to the change before merge.

At minimum, the release gate covers:

**Type safety · linting · automated tests · production build · migration safety**

The exact commands and test suites belong to the testing specification and the repository itself.

A failing required check blocks merge.

## Environments

Rule & Form uses three application environments.

### Local

Local development uses non-production data and services.

It is safe to seed, reset, regenerate, corrupt, and delete test data.

Local development does not connect to production customer systems by default.

### Preview

Every meaningful branch can run as a deployed preview.

Preview environments use non-production data and provider connections.

They cannot modify live customer records, publish over customer websites, send through customer messaging accounts, or operate against production provider resources.

### Production

`main` deploys the production application.

Production contains real customer data and real provider connections.

Only reviewed code from the canonical repository runs there.

A separate staging environment is added when operating reality gives us a reason to maintain one.

## Public demo

The public demo runs the real Rule & Form application against a dedicated demo tenant containing synthetic data.

It may share production application code. It does not share customer identity, data, provider mappings, publishing targets, messaging resources, or writable external resources with a real customer.

Demo isolation uses the same tenant-boundary rules as the rest of the application, plus dedicated demo provider configuration where an external action is required.

A public demo action must be incapable of affecting a customer account.

## Tenant isolation

Tenant isolation is explicit in application data access.

Every operation on tenant-owned data carries the relevant account or business identifier into the data-access layer.

Queries against tenant-owned tables apply that scope at the database query itself.

Conceptually:

```text
request
↓
authenticated actor
↓
authorized account / business
↓
scoped data operation
↓
WHERE organization_id = current organization
```

This rule applies equally to customer requests, internal tools, webhooks, background jobs, provider commands, and reconciliation work.

We do not retrieve global customer data and rely on frontend filtering.

We do not rely on database Row Level Security as the primary tenant-isolation mechanism. Privileged server processes can operate outside user-scoped database policies, so tenant scope remains mandatory in application data access.

Database policies may add defense in depth. They do not replace explicit tenant scoping.

Authentication answers **who is acting**.

Tenant scope answers **which data that action can reach**.

## Database changes

Database structure changes through version-controlled migrations.

```text
Change schema
↓
Create migration
↓
Validate against non-production data
↓
Commit with application code
↓
Preview
↓
Deploy safely
```

Production tables are not changed through undocumented manual edits.

Repository history must contain enough information to reconstruct the schema.

Schema changes must account for the fact that application code and database state do not change atomically.

Where a change would otherwise break an adjacent deployment, use an expand-contract sequence:

```text
Add compatible structure
↓
Deploy code that supports both states
↓
Move data / behavior
↓
Remove obsolete structure later
```

## Rollback

Application code can be returned to a known previous deployment.

Database migrations do not automatically roll back with application code.

Production migrations are therefore treated as forward-moving changes and must remain compatible with the deployment states that can legitimately coexist during release.

A destructive schema change is not coupled blindly to the first deploy that stops using the old structure.

Rollback strategy is part of the migration, not something invented after the release fails.

## Backups and recovery

Production customer data requires automated database backup and point-in-time recovery, or an equivalent recovery capability.

Recovery configuration, retention, and restore procedures are operating requirements, not assumptions.

A backup is only useful if it can be restored. Recovery is tested periodically against non-production infrastructure.

Exact retention and recovery objectives belong in the data-recovery specification rather than being frozen here.

## Secrets and configuration

Secrets never live in source code.

Local secrets live in ignored environment configuration.

Hosted secrets are scoped to the environment that requires them.

Server-only credentials never reach the browser.

Provider tokens do not appear in logs.

Production credentials are not copied into preview merely to make a test easier.

Required environment configuration is schema-validated when the application starts. Missing or invalid required configuration fails visibly rather than allowing the application to start in an unknown state.

## Observability

Thrown exceptions are only one class of failure.

Rule & Form must also expose the state of asynchronous and external work.

The operating picture includes:

**Application errors · structured logs · workflow runs · provider commands · provider events · audit history**

A publishing run stuck in retry is visible.

A failed provider command is visible.

A webhook that arrived but failed processing is visible.

The detailed event model, retention, alerting, and operating views belong in the observability specification.

## Development workflow

Cursor, Claude Code, Codex, MCP-connected tools, and other development interfaces operate against the same repository.

They are not architectural dependencies.

No development tool gets its own source of truth.

Before changing an existing subsystem, an agent should inspect:

1. the current repository,
2. the relevant Build Spec pages,
3. existing tests and migrations,
4. the current provider boundary where applicable.

The Build Spec defines intent and invariants.

The repository defines the implementation that exists now.

When the two conflict, the conflict should be surfaced and resolved deliberately rather than silently rewriting one to match the other.

## Deployment

Application deployment follows Git.

```text
Local change
↓
Feature branch
↓
Repository CI
↓
Preview deployment
↓
Review
↓
Merge to main
↓
Production
```

Application deployment does not require manual file copying or undocumented production edits.

Long-running publishing and provisioning work executes independently of the browser request that initiated it.

Closing a browser does not terminate a deployment.

A provider failure does not require replaying successful steps from the beginning.

## Infrastructure boundary

Hosting, database hosting, storage, authentication libraries, workflow runners, and external execution platforms are infrastructure.

They can change.

Rule & Form's domain objects and operating rules remain stable across those changes.

Current examples include:

```text
Application hosting
    Vercel

Database contract
    PostgreSQL

Website publishing
    Framer

Communications
    Provider adapter

Scheduling
    Provider adapter

Workflow execution
    Durable workflow layer
```

The named current provider documents what exists.

It does not grant permission to couple domain logic to that provider.

## What we do not build

We do not build generic infrastructure for its own sake.

Rule & Form does not need its own database engine, authentication protocol, object-storage service, deployment platform, telecom carrier, or distributed workflow runtime.

Engineering effort goes into the parts that accumulate product knowledge:

trade schemas · intake logic · Business Record structure · content state · rendering rules · publishing safety · provisioning logic · operational model · integrations · inspection tooling.

## Foundation rules

1. **One repository is the source of truth for application behavior.**
2. **`main` is production.**
3. **Every meaningful change is previewable before merge.**
4. **Required CI checks block unsafe merges.**
5. **Non-production cannot affect production customer systems.**
6. **Every tenant-owned data operation carries explicit tenant scope.**
7. **Database migrations are versioned and deployment-compatible.**
8. **Code rollback never assumes database rollback.**
9. **Production data has a tested recovery path.**
10. **Required configuration is validated before the application operates.**
11. **Observability includes asynchronous work, not only application exceptions.**
12. **Provider-specific code stays behind integration boundaries.**
13. **Development tools may change without changing the source of truth.**
14. **The Build Spec defines constraints and intent. It does not replace inspection of the working system.**

**The repository is the application. The Build Spec defines the constraints it must preserve.**
